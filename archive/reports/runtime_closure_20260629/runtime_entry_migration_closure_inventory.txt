4. Unsafe to migrate without larger refactor

These are execution-producing but sit inside the execution machinery itself. They should not be migrated casually into RuntimeRouteRegistry because doing so could create recursive admission, alter runtime authority semantics, or blur runner ownership.

- Scheduler.tick
  - core/tasks/scheduler.py:595
  - Current path: RuntimeNativeMainline wrapper, then scheduler dispatch pipeline.
  - Unsafe reason: tick is the scheduler event loop and owns dispatch timing/evidence.

- Scheduler.run_one_step
  - core/tasks/scheduler.py:819
  - Current path: RuntimeNativeMainline wrapper, then _execution_pipeline_run_one_step.
  - Unsafe reason: this is inside scheduler execution machinery, not an outer admission point.

- Scheduler._run_step_via_task_runner
  - core/tasks/scheduler.py:1156
  - Current path: RuntimeDispatcher.run_scheduler_boundary -> TaskRunner -> StepExecutor.
  - Unsafe reason: formal execution boundary with authority handoff; registry wrapping here would risk changing execution gateway semantics.

- Scheduler._run_task_via_agent_loop and _run_task_via_agent_loop_with_fallback_check
  - core/tasks/scheduler.py:765 and core/tasks/scheduler.py:1510
  - Current path: direct AgentLoop compatibility fallback.
  - Unsafe reason: fallback/yield logic decides whether scheduler-owned simple runner should proceed; migration needs a scheduler-level route design.

- Scheduler._run_scheduler_owned_simple_task_until_stop
  - core/tasks/scheduler.py:844

- TaskRunner.execute_owned_step

- TaskRunner.execute_owned_steps

- TaskRunner.run_task_tick / run_one_step / run_task / run

Non-mainline issue notes

- RuntimeRouteRegistry coverage is now strong for the selected AgentLoop runtime/code-chain entries, but CLI/Scheduler/TaskRunner still expose compatibility entry paths that bypass the registry while entering RuntimeNativeMainline directly.

- Direct CLI control/status/read-only paths are acceptable when they only inspect or update lifecycle status, but state-mutating maintenance commands should continue to mark themselves non-mainline or control-plane-only in output/evidence.

- Scheduler and TaskRunner are not good Package 8 first targets unless the migration explicitly models recursion, authority propagation, terminal evidence, and RuntimeDispatcher boundaries.

- The most valuable closure step is to introduce route keys for CLI outer admissions first. That preserves the principle:
  CLI/AgentLoop/Scheduler outer admission -> RuntimeRouteRegistry -> RuntimeNativeMainline.run_compatibility_entry -> existing callable.

- Non-mainline issue reporting appears preserved in the work-package CLI report surface via non_mainline_findings, and engineering goal/portfolio/program summaries carry issues_found/blocking_issues/deferred_issues. Future migrations should keep those payload fields intact when wrapping CLI callables.
